# Dogfood 6: 2026-11-22 to 23

Run 13 of migate's end-to-end runs; migate `28f651c`, then `930cd21` and `42be608` for the four fixes this run led to. How runs are
judged, and the others: `README.md`.

## What changed in the method

Dogfood 5 ran one project. This run drives twelve **profiles** through one pipeline: each names a clone (never the
project's own folder), how that project really migrates, seeds and tests, its cases, and where its ground truth lands.

| Profile | Engine | Cases | Ground truth |
|---|---|---|---|
| The origin project (Payload on D1) | SQLite (D1 local) | 36 | its own API and admin suites, data counts |
| A Supabase app | PostgreSQL 17, the real Supabase CLI with a small shim for Supabase's roles | 10 | deploy and data counts only: no runnable tests |
| A dbmate-style raw-SQL app | PostgreSQL 18, dbmate's apply logic | 10 | deploy and data counts only (its pgTAP suite needs Docker) |
| A Wrangler D1 project with two migration sets | SQLite (D1 local), `migrations_dir` | 3 | deploy and data counts only |
| documenso (open source) | PostgreSQL 15, its pinned Prisma 6.19 | 10 real + 2 built | deploy and data counts only |
| netbox (open source) | PostgreSQL 16, its pinned Django 6.1, 815 migrations | 4 | deploy and data counts only |
| Sample apps: Django, Rails, Prisma, Drizzle on PostgreSQL; Django, Rails on SQLite | both | 24 | their own tests, data counts |

Before the run, a blind reviewer read the harness alone and found, among others: a disk leak in the no-test ground
truth, seeds failing silently and still scored as "data kept", a Supabase profile on the wrong PostgreSQL major, Rails
dropped-column cases scored "safe" although a running Rails process caches its columns, and runs that would record a
harness commit not containing their profiles. All were fixed first. The scorer was then calibrated on two stub binaries,
one passing everything and one blocking everything: the first scored every break as missed, the second every safe
change as a false alarm.

## Results

100 migate runs, median 15.5 s (netbox's full migration history takes about six minutes per run). No temporary folder or
worktree left behind.

**Where tests decide** (the origin project and the sample apps): **0 missed, 0 false alarms.**

| Outcome | Count |
|---|---|
| caught: the old version's tests break, or the deploy fails | 24 (built cases among them) |
| caught: data loss, confirmed by the count | 3 |
| caught: a break only the wider suite sees | 1 |
| correct pass | 15 |
| needs a trigger marker | 6 |
| probes ok | 3 |

The origin project's 36 cases gave the same answers as in dogfood 5. The Prisma and Drizzle sample apps did not run:
their offline package install failed for want of cached package metadata, an environment fault, not a verdict.

**Where there are no runnable tests**, the ground truth can only say whether the deploy fails and whether rows are lost,
and it repeats migate's own procedure. So 16 real changes from the Supabase app, the raw-SQL app and documenso (11 that
migate blocked, 5 it passed) went to a second blind reviewer, shuffled, with no migate output, rule or prior label. It
read each migration against the old version's code and gave a verdict with file and line citations. It agreed with the
session's own labels on all ten that had them.

| Against the blind verdicts | Count |
|---|---|
| real problem, blocked (one by luck: see below) | 5 |
| safe, passed | 5 |
| false alarm | 4 |
| a trigger swap, blocked by the trigger rule (needs a marker by design) | 1 |
| disputed: a dropped legacy table no running code reads, whose rows may matter | 1 |

The real problems: a NOT NULL column with no default that the old ORM client never sets, on two tables (every insert
fails); two large rewrites dropping tables, columns and a database role the old code uses; and a routine whose result
changed from a JSON array to an object, which the old caller silently reads as empty. migate blocked that last one
because the routine was dropped and recreated, not because it saw the change of shape: it cannot see inside JSON.

The false alarms: a unique index over a new column that is empty in every row; a unique index on a new column filled
from a sequence (migate cannot prove a backfill unique on production's data, so this one stays); a dropped routine that
only seeds and tests call; and a routine dropped and recreated with every old argument kept and a new defaulted one.

## Fixed after the run

- **A unique index with one new, empty column passes** (`8c90eb6`). NULLs never collide, so one such column is enough;
  a foreign key still needs all its columns new (`MATCH FULL`). The PostgreSQL reader now records `NULLS NOT DISTINCT`,
  under which NULLs do collide; the earlier downgrade was wrong for such indexes.
- **MG107, a migration that empties a table outright** (`d540951`). The blind reviewer found a rewrite that ran
  `DELETE FROM` with no `WHERE`, cascading to two more tables; the seed held no rows there, so the row count (MG105)
  lost none and nothing said so. MG107 reads `DELETE` without `WHERE` and `TRUNCATE` from the migration's text. On the
  rerun it also found, in the other rewrite, per-organisation overrides deleted and never restored, which neither the
  count nor the reviewer's sample had reached, and a reference table emptied and reloaded on purpose (a marker accepts
  that).
- **A change adding the first migrations** (`930cd21`). The base had no migrations folder; Wrangler refuses to migrate
  one, so migate said "could not check". It now stops there with a note: the old version uses nothing those migrations
  create. The harness's own ground truth had the same fault and was fixed too.

- **Django's dependency list read from the right place** (`42be608`). netbox's 4 cases were all blocked; a third blind
  reviewer, given them the same way, judged all four safe. Every block was MG005, two heads in one app: migate's rule
  took the first "dependencies" anywhere in a migration file, and one of netbox's opens with a comment using the word,
  so the parent was lost. The rule now matches the `dependencies = [` assignment. Rerun: three cases pass; the fourth
  blocks only on a CHECK added to an existing column (MG301), which migate cannot prove the old code satisfies, so it
  asks for a marker. The Django sample apps gave the same answers as before.

Rerun on `930cd21` over the four real projects (35 cases): exactly the expected changes and the new true MG107 above;
every other case unchanged.

## Not covered, or open

- The Prisma and Drizzle sample apps (8 cases) need their package metadata fetched again.
- A routine replaced compatibly (old arguments kept, new ones defaulted, same return type) still blocks (MG505); making
  it pass would turn the JSON-shape catch above into a miss. Open, for the owner.
- A revoked privilege the old version needs has no rule; a rewrite revoked `INSERT` on a table the old version writes.
- A `DELETE` inside a PostgreSQL `DO $$ ... $$` block is not read by MG107.
- For the projects without tests, the truth repeats migate's procedure; only the blind labels are independent of it.
